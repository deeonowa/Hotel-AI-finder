## 1. ML1 — «мозг агента»

**Зона:** `backend/trip_agent/agent/*`, `llm/*`, `requirements_ops.py`, `agent/prompts/*`.
**Цель:** агент понимает любые формулировки жюри, спрашивает минимум и пересобирает план без ошибок.

### P0
1. **Подключить LLM** (Пн).
   - Сделать `.env` по `.env.example`; проверить `LlmNlu` на 2–3 моделях (OpenRouter Qwen-72B,
     локально `qwen2.5:7b-instruct` через Ollama). В `health` должен быть `llm_configured: true`.
   - Если модель не поддерживает `json_schema`, клиент сам перейдёт на `json_object` — проверить логи.
   - **DoD:** `python eval/run_eval.py --mode llm` проходит не хуже rules.
2. **NLU-датасет** `eval/nlu_cases.jsonl` (Пн–Вт): 60+ фраз → ожидаемые intent + patch.
   Обязательно: опечатки, сленг («тыщ», «косарь»), относительные даты («через две недели», «после 10-го»),
   «с тёщей и двумя внуками», латиница, несколько изменений в одной фразе, вопросы vs изменения,
   инъекции. Скрипт `eval/nlu_eval.py`: точность intent, F1 по путям патча, rules vs llm.
   - **DoD:** intent-accuracy LLM ≥ 0.9, нет регрессий относительно правил.
3. **Промпт** `agent/prompts/nlu_system.md`: few-shot на каждый intent, правила дат, «не выдумывать».
   Каждое изменение промпта — прогон `nlu_eval.py` (числа в описании PR).
4. **Политика** (`agent/policy.py`):
   - `implicit_preferences`: пожилые → доступная среда; «медовый месяц» → романтика + тишина;
     «с младенцем» → лифт и ровная дорога; лето без гор → у моря.
   - Проверить лимит вопросов (≤ 2) и что при «не знаю когда» агент не зацикливается.
   - **DoD:** `avg_clarifications ≤ 0.5` на eval, нет сценария с более чем 2 вопросами.
5. **NLG** (`agent/nlg.py`): тон «живой агент Островка», 2–4 предложения, без повторов карточек.
   Проверка чисел обязательна: тест, что LLM-ответ с выдуманной ценой отбрасывается.
6. **Пересборка** — сценарии жюри: «а если на два дня позже», «бюджет меньше», «с нами собака»,
   «без бассейна можно», «ближе к морю», «давай в горы». Каждый должен дать `DiffBlock` с понятным
   «что сохранилось / что изменилось».

### P1
7. `ask_info` через LLM, строго по фактам: отель, район, климат месяца, POI рядом
   (ML2 добавит POI в контекст). Нет факта → «не знаю, уточню у отеля».
8. **Память между сессиями** (доп. задача): `user_id` → профиль стабильных предпочтений
   («всегда с собакой», «не люблю шум») → подставлять с `Source.profile`, показывать чипсом
   «из прошлых поездок». Хранилище — от FS.
9. **После покупки текстом**: «перенесите на 2 дня» после оплаты → запрос `change_dates` + расчёт
   новой цены (пересчитать план в отдельном состоянии и показать разницу).

### P2
10. LLM-выбор следующего действия из закрытого списка обработчиков (за флагом `AGENT_PLANNER=llm`).
11. Стриминг статусов («ищу…», «проверяю состыковки…») — вместе с FS.

**Вопросы к защите (готовить ML1):** почему не ReAct/LangGraph; как пересборка без поиска с нуля;
почему LLM не может выдумать цену; что будет, если LLM недоступна; как защищены от инъекций.

## 2. ML2 — «данные, ранжирование, качество»

**Зона:** `scripts/*`, `data/*`, `catalog/`, `pricing/`, `ranking/`, `validation/`, `transfer/`, `eval/`.
**Цель:** реальные данные Сочи, правдоподобные цены, честное ранжирование с объяснениями, измеримое качество.

### P0
1. **Реальный снимок отелей** (Пн, первым делом):
   ```bash
   cd scripts && python build_location.py --location sochi --dry-run   # статистика
   python build_location.py --location sochi                           # запись hotels.json / pois.json
   ```
   Скрипт писался без доступа к Overpass — **проверить маппинг тегов на живых данных** (типы,
   санатории, звёзды, дубликаты, привязку к районам, расстояние до береговой линии).
   Если Overpass недоступен: выгрузка Geofabrik (`south-fed-district`) + `osmium tags-filter`.
   - **DoD:** 300+ реальных объектов, все 7 районов покрыты, `pytest` зелёный,
     `/api/v1/health` → `data_source: osm`.
2. **Климат** уже собран из Open-Meteo (берег и горы, 2019–2025). Проверить адекватность чисел;
   при желании — отдельная точка для Лазаревского.
3. **Калибровка DEMO-цен** (`pricing/demo_pricing.py`, `scripts/synth.py`): уровни по типам и
   звёздам, сезонность Сочи, праздники. Проверка: бюджет 60 / 100 / 150 / 250 тыс. на семью из
   трёх на неделю в ноябре и в августе даёт разумное число вариантов.
   - **DoD:** таблица в PR «бюджет × месяц → число вариантов и медиана».
4. **Ранжирование** (`ranking/baseline.py`, `ranking/prefs.py`):
   - калибровка весов на eval; `best_value` действительно дешевле, `comfort` действительно лучше;
   - разнообразие (если район не задан — по возможности разные районы);
   - человеческие тексты в `why` / `tradeoffs` / `fit_warnings` («кому не подойдёт» — главная фишка
     для истории про отели);
   - **DoD:** 0 нарушений жёстких требований на всех сценариях; тесты на новые правила.
5. **Валидатор** (`validation/rules.py`): дети и вместимость, поздний заезд, ранний отъезд,
   депозит за животное, даты в прошлом, «бюджет на ночь» × ночи.
6. **Eval** (`eval/scenarios.jsonl`): расширить с 25 до 50+. Больше незнакомых формулировок,
   конфликтов («5 звёзд за 3 000»), «без моря», «с бабушкой на коляске», сюжетов пересборки.
   Прогон в двух режимах, отчёт `eval/report.md` — в README.
   - **DoD:** `completion_rate ≥ 0.9` (llm), `constraint_violations = 0`, `crashes = 0`.

## 5. Git

- **Репозиторий — организаторов.** Перенести скелет с историей (вариант, если там уже есть файлы):
  ```bash
  cd OstrovokHotel
  git remote add origin <url-репозитория-организаторов>
  git fetch origin
  git merge origin/main --allow-unrelated-histories   # если в их main уже что-то есть
  git push -u origin main
  ```
- Ветки: `ml1/<задача>`, `ml2/<задача>`, `fs/<задача>`. Маленькие PR, слияние в `main` минимум
  2 раза в день. **`main` всегда зелёный:** `ruff check`, `pytest`, `eval/run_eval.py`, `npm run build`.
- Коммиты: `feat:`, `fix:`, `data:`, `docs:`, `test:`, `refactor:` + суть по-русски.
- Изменение `schemas/` или `ports.py` — PR, который одобрили все трое; затем FS перегенерирует типы.
- **Никогда в git:** `.env`, ключи, `var/`, `node_modules`.
- Вайб-кодить можно, но каждый **объясняет каждую строку своего модуля** — так требуют организаторы.

## 6. Сценарий демо (видео и защита)

1. Размытый запрос: «Хотим с женой и сыном 6 лет к морю, до 120 тысяч, нужен бассейн» →
   **один** вопрос «когда?» + чипсы «я понял так».
2. «В ноябре на неделю» → 3 варианта-компромисса, «почему / чем жертвуем / кому не подойдёт»,
   шкалы критериев, панель «что я сделал» (98 → 91 → 77 → 3).
3. «А если на два дня позже?» → diff: отель сохранён, цена ±.
4. «С нами едет собака» → жёсткий фильтр (неизвестная политика ≠ можно), пересборка.
5. «Сравни» → таблица. Выбор → «Во сколько вы в Сочи?» → «Утром» → проблема «ждать 5 ч» → кнопка
   «Ранний заезд» в корзину.
6. «Оформить» → «Оплатить» (имитация) → заказ OST-…; после покупки — «напомнить о поездке».
7. Невозможный запрос («5 звёзд за 10 тысяч») → честное «нет» + ослабления с числом вариантов.
8. Промпт-инъекция → спокойный отказ.
9. Показать: `eval/report.md`, `container.py` (замена поставщика одной строкой), второй Location Pack (если P2).
